# Initial architecture decision

Status: selected for the first local alpha; Foundry runtime compatibility is unverified.

## User outcome

A PF2e GM types `@assistant` in Foundry chat or uses an assistant window. The assistant searches permitted installed compendiums, proposes an NPC, stocked merchant, or encounter, and shows the source records and documents it intends to create. Only a GM click in that Foundry window applies the proposal. Local Codex and Claude clients can use the same read and proposal tools through MCP.

## Chosen shape

Use Candidate B's browser-owned plan and import domain. A small Node companion owns the provider key and an authenticated loopback connection. A separate SDK stdio entry point proxies MCP calls to that running companion. No general command router, arbitrary updates, macros, deletion tools, hosted service, or plugin framework.

- Foundry module: chat interception, accessible assistant window, connection settings, compendium adapter, immutable pending plans, previews and approval/import receipts.
- Companion: loopback HTTP and outbound browser WebSocket pairing, bounded request routing, BYOK provider requests. It accepts one paired GM browser/world at a time.
- MCP entry point: official SDK discovery and read/proposal/status tools. It connects to the existing companion rather than opening another server port.
- Shared pure functions: creation request validation and PF2e encounter math. Use plain ES modules and Node's test runner; no compilation pipeline.

A plan has one kind (`npc`, `shop`, or `encounter`), a name/background, permitted compendium UUIDs with bounded counts, and optional explicit party level/size/threat. The browser resolves those UUIDs into actual source records before preview. It owns `pending -> applying -> complete|partial`, plus `rejected`. The companion and MCP have no approval or import method. Capture source data for the preview and reject a changed source on approval rather than silently applying different data.

NPCs import canonical NPC actors with a chosen display name and background. Shops create PF2e merchant loot actors with canonical physical inventory, retaining embedded item references. Encounters import the requested NPC copies and a GM-only journal roster with quantities and calculated XP. Scene placement and combat activation are deferred.

Default permitted packs are PF2e system Actor/Item packs. Additional module packs require GM configuration. Search index fields first and load only selected documents. External reads return bounded source summaries and party metadata; no unrestricted journal/world export. Text generated by a provider is escaped before HTML insertion. Never accept executable document data from a model.

## Pairing and credentials

Bind to `127.0.0.1`. Check Host and the exact configured Foundry Origin; authenticate the first WebSocket message, not a secret in a URL. HTTP proxy requests also require a companion token. Reject unknown operations and oversized frames/bodies. The provider key exists only in local environment configuration and outbound provider Authorization, never in module settings or MCP results/logs. Sanitize provider errors.

The first supported deployment target is a browser on the companion machine with HTTP Foundry. Hosted HTTPS and remote ChatGPT web connectors need a separately verified secure transport/deployment; do not present localhost stdio as a cloud connector. Foundry 13-14 are intended targets, not certified compatibility claims. Native Claude API is deferred; Claude's local MCP client can already propose plans.

Use OpenAI Responses for the initial in-panel BYOK provider. Current OpenAI model families can require Responses for tool calling. Keep the endpoint/model configured explicitly and preserve function call outputs correctly. A model-free MCP caller can search sources and supply a structured creation proposal without a paid model request. No real paid request is necessary to run verification.

## Rules and failure behavior

Verified against [GM Core Combat Threats](https://2e.aonprd.com/Rules.aspx?ID=2716): four-PC thresholds 40/60/80/120/160; each extra or missing PC adjusts those by 10/20/20/30/40. Relative creature levels -4 through +4 cost 10/15/20/30/40/60/80/120/160 XP. The earlier local design's low-threat adjustment of 15 was incorrect and rejected. Compute from resolved creature levels, not model arithmetic. Reject unsupported proficiency-without-level calculations and missing party inputs.

Single-flight approval and per-step receipts prevent duplicate clicks and support explicit retry of remaining steps after a partial failure. Give planned creations stable IDs and provenance flags, reconcile existing IDs before retry, and stop after the first failure. Never delete completed imports or auto-retry world writes. Pending plans are session-scoped; browser refresh discards them and does not replay completed imports. Durable approval journals and cross-restart replay are deferred.

## Design comparison

Scores are 1-5; columns are workflow, trust boundary, small API, retry handling, and rules/compatibility.

| Design | Parent scores | Independent judge scores |
| --- | --- | --- |
| A: companion owns plans | 5,5,3,5,3 | 5,5,3,5,3 |
| B: browser owns plans | 5,5,4,3,4 | 5,5,4,3,4 |

Both converge on a local companion and GM-owned writes. Select B for fewer state owners and the smaller API. Graft A's single-browser ownership and stable operation identity. Its durable journal/file store is outside this first alpha; state loss on refresh is explicit. No candidate dropped out. The judge simultaneously suggested and rejected a durable journal; the parent resolved that inconsistency in favor of session-scoped plans with persistent document provenance, rather than an extra persistence service.

## Acceptance and verification limits

Automated checks must exercise budget math, invalid requests, permitted compendium resolution, zero writes before approval, actor/stock/roster creation, duplicate approval, partial retries/source drift, origin/auth rejection, a fake provider tool loop, and SDK MCP discovery/calls against the running companion. Package the actual module files and inspect the archive. These are required checks, not results.

Live Foundry chat, rendering, PF2e embedded data and browser connectivity need testing in Tom's disposable world before this is called usable in a campaign. Record actual commands/results and any unavailable checks in README/verification evidence.

## Throughput checkpoint

- Blocking first steps: account/private repo and source licenses verified; rule table corrected before implementation.
- Independent workstreams: monetization uses a separate read-only chat; designs used separate artifacts and a completed-candidate judge.
- Shared mutable state: one implementation owner gets an exclusive Git worktree; integration/review occur after that owner stops writing.
- Smallest safe decomposition: browser/companion protocol is one coupled feature owned by one writer. Independent review follows its immutable candidate commit.
